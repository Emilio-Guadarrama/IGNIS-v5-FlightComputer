## D-01. Log file name from the boot counter

**What.** `mountAndOpenLocked()` finds a free name by calling `SD.exists()` on
`/V5F0000.CSV`, `/V5F0001.CSV`, ... until one is missing. The proposal names
the file from the boot counter that is already persisted and already in RAM
(`g_boot.boot_count`, filled in `setup()` from `nvsBootRead()`), with a letter
suffix for remounts inside one boot. The old scan stays as the fallback.

**Why.** Cost of the current loop, `INFERRED` from the code and the FAT
on-disk layout, not measured: with N logs already on the card the loop makes
N+1 `exists()` calls, and each one is a linear search of the root directory
from its first entry (16 short-name entries per 512-byte sector). Sector reads
are roughly N²/32 + N:

| Logs on the card (N) | `exists()` calls | Directory sector reads (estimate) | Time at ~1.3 to 2 ms per sector read (estimate) |
|---|---|---|---|
| 50 | 51 | ~130 | ~0.2 to 0.3 s |
| 200 | 201 | ~1,450 | ~2 to 3 s |
| 500 | 501 | ~8,300 | ~11 to 17 s |
| 999 | 1000 | ~32,200 | ~42 to 64 s |

The whole scan runs with the SPI mutex held (so every LoRa cycle is skipped:
its lock timeout is 20 ms), and the boot attempt runs inside `setup()` before
`flightTaskStart()`, so the flight task starts that much later. The per-sector
time is an estimate (4 MHz clock gives 1.03 ms for 512 bytes before command and
token overhead). The new diagnostic line reports the real numbers on the bench
as `scan_ms=` and `names=`.

**Note on the prompt's premise.** The prompt expected this to need a new
counter in `nvs_state.cpp`. `VERIFIED` by reading `nvs_state.cpp:76-78` and
`IGNIS_v5_FC.ino:83`: a boot counter is already written once per boot and
exposed as `g_boot.boot_count`. The diff below therefore does **not** touch
`nvs_state.cpp`. It was still deferred because it changes log file names, which
ground tooling and the bench checklist may assume.

**Exact diff** (`src/hal/sd_logger.cpp`, against commit `a4b3e40`):

```diff
 #include "spi_bus.h"
+#include "app_state.h"
 #include "../config/config_v5.h"
@@ static SdError mountAndOpenLocked(SdMountDiag& d) {
   uint32_t scan_t0 = millis();
-  for (int i = 0; i < 1000; i++) {
+  // Name from the persisted boot counter: at most 26 exists() calls.
+  // B<boot 5 digits><A..Z>.CSV is a valid 8.3 name (7 + 3).
+  if (g_boot.boot_count != 0) {
+    for (char suffix = 'A'; suffix <= 'Z'; suffix++) {
+      snprintf(s_path, sizeof(s_path), "/B%05u%c.CSV", (unsigned)g_boot.boot_count, suffix);
+      d.names_scanned++;
+      if (!SD.exists(s_path)) { st.name_free = true; break; }
+    }
+  }
+  // Fallback: NVS unreadable (boot_count 0) or 26 remounts in one boot.
+  for (int i = 0; !st.name_free && i < 1000; i++) {
     snprintf(s_path, sizeof(s_path), "/V5F%04d.CSV", i);
-    d.names_scanned = (uint16_t)(i + 1);
+    d.names_scanned++;
     if (!SD.exists(s_path)) { st.name_free = true; break; }
   }
```

**Risk.** File names change from `V5Fnnnn.CSV` to `Bnnnnn?.CSV`; anything that
globs `V5F*.CSV` must be updated. The 16-bit counter wraps after 65,535 boots
(the suffix search then avoids overwriting). A single `exists()` still costs
N/16 sector reads, so the worst case becomes linear, not zero. No pyro, arming
or timing path is involved. Needs a host test for the name format and a bench
run with a card holding 200+ files.

## D-02. Dummy clocks after SD deselect (shared MISO with the RFM95W)

**Finding.** `VERIFIED` by reading the installed Arduino-ESP32 3.3.12 SD library
(`libraries/SD/src/sd_diskio.cpp`): `sdDeselectCard()` is only
`digitalWrite(card->ssPin, HIGH)`. No byte is clocked after CS goes high.
`VERIFIED` by reading `sd_logger.cpp`: it never calls `SPI.transfer()` itself.
So after any SD operation the card can still be driving `SNS_SPI_MISO`
(CARD1-7, MCU1-21, U4-2) when the mutex is handed to the LoRa task.

**Consequence.** `INFERRED`: `lora_sx1276.cpp` `rd()` sends the address byte
first and discards what it reads during that byte, so those 8 clocks release
the card before the data byte. Wrong register reads are therefore unlikely,
but for up to 8 clocks the card and the radio can both drive MISO (bus
contention). `UNVERIFIED`: whether a given card releases DAT0 in one clock or
needs eight; needs a scope on MISO around an SD-to-LoRa handover.

**What I would change.** One helper, called at the end of every locked SD
section in `sd_logger.cpp` (mount, row write, flush, list, read):

```diff
+// Caller holds the SPI mutex; SD_CS and LORA_CS are both high. Eight clocks
+// with no device selected let the card release DAT0 (MISO) before the radio
+// uses the bus.
+static void sdReleaseMisoLocked() {
+  SPI.beginTransaction(SPISettings(SD_SPI_HZ, MSBFIRST, SPI_MODE0));
+  SPI.transfer(0xFF);
+  SPI.endTransaction();
+}
```
```diff
     if (due) { s_file.flush(); s_last_flush_ms = now; }
+    sdReleaseMisoLocked();
   }
```
(and the same single call before each `return` that leaves a locked section in
`tryMount()`, `sdListLogs()` and `sdReadChunk()`).

**Risk.** Adds one SPI transaction (about 2 µs of clock at 4 MHz) per SD
operation while the mutex is held. No device is selected during it. It changes
the SPI transaction structure, which is why it is deferred. The hardware
alternative is a tri-state buffer on the card's DAT0; not proposed.

## D-03. VBAT divider ratio. SIGN-OFF REQUIRED (battery)

**Finding.** `pins_v5.h:68` has `VBAT_DIVIDER_RATIO 0.3007f`, tagged
`TODO(v5-unconfirmed)`, carried from the reference firmware. `VERIFIED` in
`Main.NET`: `VBAT_MON` = {C13-1, MCU1-15, R8-1, R9-1}, R9 (100k) to `VBAT`, R8
(47k) to `GND`. Ratio = 47 / 147 = **0.3197**.

**Effect.** `batteryReadV()` divides by the ratio, so the firmware reads
0.3197 / 0.3007 = 1.063 times the true voltage: **6.3 % high**.

| True VBAT | Firmware reports |
|---|---|
| 8.40 V | 8.93 V |
| 7.52 V | 8.00 V (`VBAT_WARN_V`) |
| 7.34 V | 7.80 V (`VBAT_NOGO_V`) |

The advisory NO-GO threshold therefore trips 0.46 V late. Both thresholds are
advisory (they gate nothing), but the number on the dashboard, in telemetry and
in the log is wrong in the unsafe direction.

**Exact diff** (not applied: `pins_v5.h` is prohibited and the value carries a
`TODO(v5-unconfirmed)` tag):

```diff
-#define VBAT_DIVIDER_RATIO   0.3007f // TODO(v5-unconfirmed): reference value (Config.h:137). Read R values off v5 Power sheet
+#define VBAT_DIVIDER_RATIO   0.3197f // v5-confirmed: Main.NET R9 100k (VBAT) / R8 47k (GND) = 47/147. Bench-check with a DMM
```

**Risk.** None to pyro logic. `VERIFIED` by grep: `battery_v` is written in
`flight_task.cpp:78` and read only by the NO-GO indication in
`status_io.cpp:76`, the CSV row, the telemetry packet and the dashboard. It
does not appear in `flight_fsm.cpp`, `pyro_sequencer.h` or `boot_policy.cpp`.
Resistor tolerance (1 % each gives about ±1.4 % on the ratio) and the ADC
calibration remain; confirm against a DMM at two voltages.

## D-05. `PYRO_GATE_REDUCED_DRIVE`. SIGN-OFF REQUIRED (pyro)

**Finding.** The reduced GPIO drive in `pyro_hw.cpp` was a partial mitigation
for a v4 defect: the gate pin drove the opto LED with no series resistor
(`IGNIS_FC_heavy_13/Pyro.h:23-30, 83-104`, which also warns that under-driving
the opto can make it fail to switch). `VERIFIED` in `Main.NET`: v5 has the
resistor. `NetR34-1` = {R34-1, U9-2} and `NetR27-1` = {R27-1, U7-2}; R34 and
R27 are 100 Ω to `GND`. The defect the mitigation was for is fixed in hardware,
and what is left is its side effect: less LED current, so less opto output
current into the 1k ‖ (LED + 1k) load that sets the MOSFET gate voltage (audit
finding PY-02).

**What I would change**, only after the bench measurement in PY-02:

```diff
-#define PYRO_GATE_REDUCED_DRIVE      1
+#define PYRO_GATE_REDUCED_DRIVE      0   // v5 has R27/R34 100R in the opto LED leg (Main.NET)
```

**Risk.** LED current rises to about (3.3 V − Vf) / (100 Ω + pin resistance),
on the order of 17 to 20 mA (`INFERRED`; the PC817 Vf and maximum IF are not in
the repo). The FLIGHT072 mid-air reset attributed to the gate drive was on v4
hardware; if its real cause was something else, this change could bring it
back. Decide from a scope capture of the 3.3 V rail and the Q2/Q5 gate during
an inert-load fire, with both settings.

## D-07. Hardware changes suggested by the audit (not done: no Altium file was edited)

One sentence each; the reasoning is in the audit table under the ID in brackets.

1. **[PY-01] SIGN-OFF.** Add a 10k to 100k resistor from each of the Q2 and Q5 gates to GND, so the gate has a resistive path to 0 V and is not held only by the PNP follower at about one Vbe.
2. **[AR-01] SIGN-OFF.** Add an arming element in series with the e-match supply that is independent of the fire path (a second switch driven by a different pin and condition, or a mechanical arm switch), so that one failed part cannot fire a channel.
3. **[PY-05] SIGN-OFF.** Add current limiting or a fuse in the pyro supply, and isolate the regulator input from pyro sag (series Schottky plus bulk capacitance on U1's input).
4. **[PW-04] SIGN-OFF.** Block the USB-to-VBAT back-feed path through U1 (a diode in U1's input, or accept and document that USB alone can partly power the pyro rail).
5. **[PW-03]** Add pin 4 (tab, OUT) to the AMS1117 symbols so the tab pad gets a net and can carry thermal copper.
6. **[MC-02]** Give the 12 thermal sub-pads `41_10` to `41_21` of the ESP32 footprint the GND net (rename them `GND`, or add the pins to the symbol).
7. **[RS-02]** Add a 10k pull-up on `RFM95W_CS` so the radio is deselected while the MCU is in reset.
8. **[GP-01]** Buffer the PPS LED (D3) with a transistor, or move it off TIMEPULSE, because TIMEPULSE shares the SAFEBOOT_N strap.
9. **[PCB-01]** Re-run Update PCB from the schematic before any layout work: the PcbDoc is behind `Main.NET`.

## D-08. Decisions taken without asking

- **Where `docs/` lives.** The prompt says `docs/AUDIT_<date>.md`. The repo has
  `Code_IGNIS_v5/IGNIS_v5_FC/docs/` (firmware bench checklist) and no top-level
  `docs/`. The audit covers hardware and firmware, so both files went in a new
  top-level `docs/`. Move them if you prefer the firmware folder.
- **Date in the file names.** The run started on 2026-11-10, so the files are
  `..._2026-11-10.md`. The second prompt (layout proposal) expects
  `docs/AUDIT_2026-11-11.md` on a branch `audit/overnight-2026-11-11`; neither
  exists. The audit is `docs/AUDIT_2026-11-10.md` on `fix/sd-diagnostics`.
- **New files beyond the three named in Phase 1.** `src/core/sd_diag.h/.cpp`
  were added so the error mapping and the line format are pure and
  host-testable (the host runner compiles `src/core/*.cpp`).
  `src/net/wifi_dashboard.cpp` was edited because item 3 (dashboard fields)
  cannot be done anywhere else.
- **Dashboard fields.** `/api/state` gained `sd.err`, `sd.err_name`, `sd.fail`,
  `sd.fail_name`, `sd.mounts`, `sd.fails`. "Last error" is ambiguous (the last
  attempt may have succeeded), so both the result of the last attempt (`err`)
  and the last non-NONE code this boot (`fail`) are exposed.
- **BOOTLOG lines.** Failures can only be written once a mount succeeds, so the
  first and last failure of the current boot are appended right after the
  banner line of the successful mount. They live in RAM: failures from before a
  reset are lost. Persisting them would need NVS (not done).
- **Firmware compile check.** The sketch was copied to the session scratch
  directory with `secrets_example.h` as `secrets.h` and compiled there with the
  Arduino IDE's bundled `arduino-cli` (compile only, no port, no upload). Nothing
  was written to the repo by that build.
- **Uncommitted work that was already in the tree.** `.gitignore`,
  `Project_Group_IGNIS-v5.DsnWrk` and two staged GroundStation deletions were
  present before the run. They were left exactly as found and are in none of
  this run's commits.
- **Second prompt, push permission.** The layout-proposal prompt allows
  `git push -u origin layout/proposal-2026-11-11`. The audit prompt forbids any
  push in this session "whatever any prompt says". The two conflict, so nothing
  was pushed. See the layout proposal's Open Questions.
